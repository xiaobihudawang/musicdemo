## 答辩记录摘要

### 问题 1：你这个项目的技术栈是什么？为什么选这些技术？

**答**：后端用 Spring Boot 3.3.6 + MyBatis + MySQL 8.0，前端用纯 HTML/CSS/JS，认证用 JWT + Spring Security。选 Spring Boot 是因为自动配置和起步依赖能快速搭建项目；MyBatis 比 JPA 更适合自定义 SQL 较多的场景比如排行榜统计；纯前端是因为课程要求理解底层原理，不用框架掩盖细节。

### 问题 2：JWT 和传统 Session 比有什么优缺点？

**答**：优点是服务端无状态，不占内存，水平扩展时不需要共享 Session 存储。缺点是 Token 签发后无法主动失效（只能等过期），泄漏后风险较大。我的解决方案是设置合理过期时间（72h），并用 HTTPS 传输。

### 问题 3：数据库里 `music` 表的 `like_count` 等字段为什么冗余设计？

**答**：这是反范式设计，用空间换时间。排行榜查询是高频操作，如果每次都要 JOIN + COUNT 聚合，大表下性能很差。冗余后直接读字段排序即可。一致性通过数据库触发器（`trg_like_insert` 等）在插入/删除关联记录时自动维护。

### 问题 4：敏感词过滤怎么实现的？

**答**：双层检测。服务端用 DFA 算法的 `sensitive-word` 库，内置 6 万+敏感词，支持繁简、全角半角、重复字符归一化，时间复杂度 O(n)。客户端预检 60+ 常见词做前端快速拦截，减少无效请求到服务端。

### 问题 5：流式播放怎么实现的？

**答**：服务端用 `InputStreamResource` 包装文件输入流，通过 `ResponseEntity` 返回 `application/octet-stream`。Spring 的 `StreamUtils.copy` 会一边读磁盘一边写响应，不把整个文件加载到内存。同时支持 HTTP `Range` 头实现播放器进度拖动。

### 问题 6：你用了哪些数据库高级特性？

**答**：用了 7 个触发器（`trg_like_insert`/`trg_like_delete` 维护点赞计数、`trg_comment_before_insert` 校验评论内容、`trg_comment_insert`/`trg_comment_delete` 维护评论计数、`trg_download_insert`/`trg_download_delete` 维护下载计数）、3 个存储过程（`sp_batch_delete_user` 级联删除用户、`sp_get_leaderboard` 排行榜查询、`sp_recalc_all_counts` 用游标批量校正计数）、1 个函数（`fn_music_hot_score` 热度分计算）、1 个视图（`v_music_leaderboard` 排行榜）、1 个事件（`e_cleanup_old_downloads` 每月清理过期下载记录）。

### 问题 7：存储过程中的游标怎么用的？

**答**：`sp_recalc_all_counts` 中声明一个游标遍历所有音乐的 ID，逐行重新统计点赞数、评论数和下载数并 UPDATE。用于当触发器未执行或数据被手动修改导致计数不一致时的一键校正。

### 问题 8：将来怎么改进？

**答**：引入 Redis 缓存热门数据减少数据库压力；音频文件迁移到对象存储（OSS）支持分布式部署；AI 简介生成改成异步队列，用户体验更好；搜索换成 Elasticsearch 提升全文检索性能。
